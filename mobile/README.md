# 安药：手机当前 1.1.0 的修复工程

本目录以用户手机上实际安装的 **com.anyao.app 1.1.0 / versionCode 2** 为基线。不是旧版 0.4.11 工程，也不是找回了原作者的 Kotlin / Gradle 源码。

输入 APK SHA256：`599372931707aab30fe00780ebbe1a9739cf307d123e89399a91717368f567d3`。原生实现包含新版的家庭同步、自动电话、手表、提醒与数据处理，不能用旧工程直接替换。

## 工程内容

- `web/`：从该 APK 提取并修复的页面源文件，保留手机当前版本的界面。
- `native/com/anyao/repair/`：新增的可审阅 Java 源码，包括库存收据、相机授权、闪光、震动与系统设置入口。
- `tools/build-current.py`：核对输入 APK 指纹，再解包、应用有明确上下文校验的 smali 补丁、编译 Java、合并 DEX、对齐并签名。
- `tests/`：界面回归与实际 APK 原生 Store 测试。测试范围在结果 JSON 中标注，不能当作设备实物验收。
- `baseline.json`：提取前的网页哈希与来源信息。

未改动的原生功能继续来自输入 APK 的 DEX。JADX 产生的反编译 Java 仅用于定位，不是可直接编译的原工程，因此没有作为原始源码交付。

## 本次修复

1. 单独保存每次库存扣减数量与库存单位，不从 `100mg` 等剂量说明猜测片数。服药、按需服药、重复提交、撤销、补药、备份恢复使用一致规则。
2. 撤销使用当时实际扣减的收据；之后改剂量不改变历史扣减量。库存不足时记录服药并提示未扣库存，库存不变负数。补药使用十进制计算并保存当时单位。
3. 剩余天数按每日次数与每次数量计算；不同单位库存不合计成总片数。
4. Android 返回键取消最上层确认框，保留下层未保存编辑；修复弹窗关闭事件与再次打开之间的竞态。
5. 家属端区分未来计划、漏服、跳过、已补记，消除“还没到时间却全部按时吃完”的误报。
6. 打开微信、短信、邮件、拨号界面后，由用户另行确认是否记录联系；不把打开或复制文字当作消息送达或电话接通。
7. 跨月查看完整服药历史；未知药盒仓位不显示第 0 仓，原始活动不作为已服药证明。
8. 显式申请闪光所需相机权限，选择背面闪光灯，兼容开关式手电筒；异常反馈真实失败原因，结束时关灯。
9. 使用旧版实机验证过的通知震动通道，并检查系统是否允许通知震动。增加系统声音与振动设置入口。
10. 补齐 vivo / iQOO 自启动设置入口；权限齐全仍提示实测锁屏提醒，不直接宣称后台可靠。
11. 连接状态下读取到电量不超过 20% 时显示低电量提示；离线时不宣称能实时监测电量。
12. 修复本机锁屏时广播消费者被冻结、闹钟到点却延后执行的问题：改为精确闹钟直接启动短时前台执行服务，完成后结束；保留去重与计划取消，迁移旧广播闹钟。实机验收结果单独记录。

13. 新增原生 Camera2 + ZXing 离线扫描及图片识别，支持 EAN-13、EAN-8、Code128、二维码等。条码可匹配当前已登记药物；未登记药物由用户核对包装填写名称。扫码不上传图片、不自动打开网址，不推断医嘱或剂量。药盒设备码会提示进入药盒页面。
14. 分类、条码、星期、各时间数量通过原生 Store 验证并持久化，完整备份恢复支持这些字段；旧备份兼容每天重复与默认扣减数量。
15. 按 ISO 星期（1=周一，7=周日）生成当天计划和最多 31 天的缺席历史，未选日期不生成计划；编辑星期及时取消当天待执行项，保留已服用/跳过记录。
16. 保存按日期生效的计划修订，改变未来用药星期不会用新规则改写历史。午夜刷新从 00:01 调整到 00:00；当天 00:00 的计划生成与跨日逻辑有独立验证，真实跨午夜执行仍需长时验收。
17. 每个时间可覆盖默认扣减数量，服药收据按当次实际数量保存，撤销不受后来改量影响；通知和详情显示当次库存单位与数量。
18. 两端提供分类筛选、药名/条码搜索；下次服药跳过未选星期，休息日显示下一次计划，库存估算按每周频率和各时间数量计算。
19. 非每日药盒计划在页面和原生蓝牙写入前拒绝，避免未经确认的星期位被当作每日下发；不会先清空设备后才报不支持。已有药盒旧计划仍须连接后重下发或清除。
20. 家庭服务未声明新增字段支持时阻止相关新字段保存，避免旧服务静默丢弃星期或数量。外部家庭服务可通过 `GET /api/capabilities` 返回 `drugFields: ["weekdays", "timeQuantities", "category", "barcode"]` 声明已实际实现的字段；本包没有部署新的家庭服务。

## 安装与数据

输出应用名为 **安药验证**，包名 `com.anyao.app.qa`，版本 `1.1.0-repair.2` / versionCode 4。它可以更新同签名验证版，与原安药并存，数据独立。原 APK 的签名密钥不在本机，不能直接覆盖原包。没有为绕过签名卸载原安药。

如要迁移正式数据，应先从原安药导出备份，再在验证版恢复并核对；不要把验证用临时药物作为正式计划。本次实机测试使用独立临时数据，测试后清理。

构建默认使用当前电脑的 Android debug keystore；密钥不包含在交付包。另一台电脑使用不同密钥重建后，不能覆盖已安装的同包名验证版。发布到原包名需要合法的原签名密钥和完整发布验证。

## 构建

从工程根目录运行：

```powershell
python -X utf8 products/anyao/mobile/tools/build-current.py
```

当前工具路径：

- `tools/android-build-env/jdk17/`：JDK 17。
- `tools/android-build-env/sdk/`：Android SDK，platforms/android-36、build-tools/36.0.0、platform-tools。
- `tools/cache/apktool_3.0.3.jar`：Apktool 3.0.3。
- `products/anyao/mobile/vendor/`：固定哈希的 ZXing Core 3.5.3 及 Apache-2.0 许可证，已随源码附带，构建不需要再次下载。
- `evidence/mobile-current-20261016/installed-1.1.0.apk`：指纹固定的输入文件。
- 用户目录 `.android/debug.keystore`：Android 开发签名。

输出 APK 和构建指纹位于 `evidence/mobile-current-20261016/`。每次构建使用新的临时目录，保留原始输入。便携交付包不捆绑大型 JDK/SDK，按上述布局准备工具后即可构建。

## 验证

```powershell
node products/anyao/mobile/tests/ui-regressions.cjs
python -X utf8 products/anyao/mobile/tools/test-native.py
python -X utf8 products/anyao/mobile/tools/test-barcode.py
python -X utf8 products/anyao/mobile/tools/test-installed.py
```

界面测试需要 Playwright 与 Chrome。可在解压根目录执行 `npm install --no-save playwright`；优先加载该依赖，也可用 `ANYAO_PLAYWRIGHT_PATH` 指定模块目录，`ANYAO_CHROME_PATH` 指定 Chrome。没有系统 Chrome 时先执行 `npx playwright install chromium`。本机附带运行时作为最后兼容路径使用。原生测试需要已授权 USB 调试的 Android 手机；它在 `/data/local/tmp` 的隔离文件上运行 APK 类，不修改原安药业务数据。

`test-installed.py` 需要 USB 调试已授权、手机解锁并打开“安药验证”，且验证版内没有正式药物计划。脚本会先检查空数据、保留私有备份，再通过实际原生桥检查 Android 返回键、进程重启持久化、星期计划及库存收据，结束时恢复原设置并清理临时数据。有正式药物时停止，不用于在线业务数据测试。

签名验签、真机安装和提醒实物反馈是额外验证，不能由上述自动测试替代。验收状态见 `docs/验证记录.md`。

## 尚未覆盖的能力

- 手机端已实现分类、离线扫码、按星期计划、逐时间数量及相应存储、调度、统计与备份。扫码只识别条码并匹配当前登记药物，没有接入覆盖全国药品的名称查询数据库，也不会声称二维码一定含有药名。
- 本台药盒的星期位映射尚无官方有效抓包，目前只有每日 `0x7f` 得到确认。因此手机的非每日计划不能直接用于药盒离线星期提醒；页面和原生均有写入前校验。
- 四仓计划、离线提醒、寻找、查询与记录同步沿用当前 1.1.0 及已验证的协议。新增包需单独复验蓝牙授权与实物效果，不能仅复用原包测试结论。
- 药盒音量、灯色、语音、童锁、OTA、官方账户解绑没有本机可靠控制指令；未添加无效开关，也未发送猜测指令。
- 真实跨手机同步、实际短信/邮件/微信送达、自动电话接通、手表认证需要对应设备/服务和明确测试对象，不能用模拟接口代替验收。
- 单台手机短时测试不能证明所有机型、手机重启或多日深度省电条件下都可靠。
